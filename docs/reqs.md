# Requirements

## Active

### Schemas

| ID         | Requirement                                                                                                                                                                                                                                                                                                                                        |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| SCHEMA-001 | A valid schema shall contain between 1 and 64 columns, inclusive.                                                                                                                                                                                                                                                                                  |
| SCHEMA-002 | Column names within a schema shall be unique under ASCII case-insensitive comparison, treating ASCII letters A-Z as equivalent to a-z and comparing all other characters exactly.                                                                                                                                                                  |
| SCHEMA-003 | Column IDs within a schema shall be unique.                                                                                                                                                                                                                                                                                                        |
| SCHEMA-004 | In a schema containing N columns, column positions shall be exactly the integers from 0 through N - 1, each occurring once.                                                                                                                                                                                                                        |
| SCHEMA-005 | Column IDs shall be independent of column positions: otherwise valid schemas shall permit distinct column IDs assigned to positions in any order, without requiring IDs to equal positions or to be contiguous. However, by default IDs will be assigned in the order of the definition in the schema & table creation statement, starting from 0. |

#### Schema Builder

| ID | Requirement |
|---|---|
| SCHEMA-BLD-001 | `build()` shall return an error when the supplied columns violate SCHEMA-001 through SCHEMA-004. |
| SCHEMA-BLD-002 | Successful construction shall preserve the supplied owner ID and each column's ID, name, type, position, and primary-key flag. |
| SCHEMA-BLD-003 | The builder shall accept and store an ordered list of primary-key column IDs through `.pk(...)` and pass that order unchanged to the built schema. |
| SCHEMA-BLD-004 | `build()` shall return an error if any column is marked as a primary key and no primary-key ordering list was supplied. |
| SCHEMA-BLD-005 | `build()` shall return an error if the primary-key ordering list supplied through `.pk(...)` contains a column ID that does not identify any supplied column. |
| SCHEMA-BLD-006 | `build()` shall return an error if the primary-key ordering list supplied through `.pk(...)` contains the same column ID more than once. |
| SCHEMA-BLD-007 | `build()` shall return an error if the primary-key ordering list supplied through `.pk(...)` omits the ID of any supplied column whose `is_pk` flag is true. |
| SCHEMA-BLD-008 | `build()` shall return an error if the primary-key ordering list supplied through `.pk(...)` includes the ID of any supplied column whose `is_pk` flag is false. |

### Binary Row Representation

| ID | Requirement |
|---|---|
| ROW-BIN-001 | Binary rows shall use the following complete layout:<br>1. Sections shall appear contiguously, without padding, in this order: header, integers, NULL bitmap, string end offsets, string data.<br>2. The six-byte header shall contain three little-endian unsigned 16-bit fields: total encoded row size at byte 0, integer column count at byte 2, and string column count at byte 4. Counts shall include NULL columns.<br>3. Each integer column shall occupy four bytes as a little-endian signed 32-bit integer, ordered by ascending schema position among integer columns. A NULL integer shall occupy four zero bytes.<br>4. The NULL bitmap shall occupy eight bytes as a little-endian unsigned 64-bit integer. Bit p shall describe the column at schema position p; 1 shall mean NULL and 0 shall mean non-NULL. Bits beyond the schema's column count shall be zero.<br>5. Each string column shall have one little-endian unsigned 16-bit end offset, ordered by ascending schema position among string columns. Offsets shall count bytes relative to the start of string data. A string shall begin at the preceding string's end offset, or zero for the first string.<br>6. String data shall contain the strings' UTF-8 bytes in the same order, concatenated without separators, terminators, or padding. NULL and empty strings shall contribute no data bytes and shall repeat the preceding end offset, or zero for the first string; the bitmap shall distinguish them.<br>7. For I integer columns, S string columns, and B total string-data bytes, the complete encoded size shall be 6 + 4 * I + 8 + 2 * S + B bytes. Lengths shall count UTF-8 bytes rather than characters.<br>8. The complete encoded row shall occupy at most 3996 bytes, including all sections, calculated as 4096 bytes per page minus the 96-byte page header minus one 4-byte slot; otherwise valid rows of exactly 3996 bytes shall be supported. Rows shall be stored entirely inline, without LOB references or continuation across pages. |
| ROW-BIN-002 | Row serialization, given a schema satisfying SCHEMA-001 through SCHEMA-005, shall behave as follows:<br>1. The row shall contain exactly one explicit cell for every schema column, including NULL values. Cells shall be matched by their complete schema-entry identity, including owner ID and column ID; row-cell order shall not affect the encoded bytes.<br>2. Non-NULL values shall match their schema column's type: signed 32-bit integer or string. NULL shall be accepted for either type, including primary-key columns.<br>3. Successful serialization shall return exactly the bytes specified by ROW-BIN-001, including complete string end offsets and string data.<br>4. Serialization shall return an error for an unknown schema-entry identity, missing cell, non-NULL type mismatch, or complete encoded size above 3996 bytes.<br>5. Failure shall return no encoded row, and serialization shall leave the supplied row and schema unchanged.<br>6. Serialization shall not panic for any supplied row or schema, including invalid inputs; rejected inputs shall produce an error. This guarantee shall apply independently of the valid-schema precondition above.<br>7. Each error shall identify the reason for rejection with enough context to understand the failure, including the offending column identity for cell-specific failures and expected versus supplied types for type mismatches. When multiple defects coexist, serialization may report any applicable error; no validation order shall be required. |
| ROW-BIN-003 | Row deserialization, given a schema satisfying SCHEMA-001 through SCHEMA-005, shall behave as follows:<br>1. Successful deserialization shall interpret exactly one complete row using ROW-BIN-001 and return one explicit cell for every supplied schema column, assigning the supplied schema's owner and column IDs. The caller shall be responsible for supplying the correct schema; encoded rows shall contain no schema identity or version, and the decoder shall not be required to detect a different schema that passes the specified format checks. Integer values, string contents, and NULL values shall be preserved; integer zero and empty strings shall remain distinct from NULL.<br>2. Deserializing a successfully serialized row with the same schema shall reproduce its column identities and values, independently of the original row-cell order.<br>3. Deserialization shall return an error for input longer than 3996 bytes, a truncated header, a header size different from the supplied byte length, header column counts different from the schema's integer and string counts, or insufficient bytes for the header, integers, bitmap, and offset array.<br>4. Deserialization shall return an error if an unused bitmap bit is set, a NULL integer has nonzero stored bytes, or a NULL string has a nonempty byte range.<br>5. String end offsets shall be nondecreasing and within the string-data section. Each individual string range shall contain valid UTF-8. The final offset shall equal the string-data length; when there are no string columns, no string-data bytes shall remain. A violation shall return an error.<br>6. Failure shall return no decoded row, and deserialization shall leave the supplied bytes and schema unchanged.<br>7. Deserialization shall not panic for any supplied bytes or schema, including invalid inputs; rejected inputs shall produce an error. This guarantee shall apply independently of the valid-schema precondition above.<br>8. Each error shall identify the reason for rejection with enough context to understand the failure, including expected versus actual sizes or counts for mismatches and the affected column or string index for column-specific failures. When multiple defects coexist, deserialization may report any applicable error; no validation order shall be required. |
